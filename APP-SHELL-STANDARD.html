App shell standard — rail, header, guide, flags, themes

Reference implementationReact · TypeScript · Tailwind · zustandPortable contracts per section

A reference implementation, taken out of the CTIO COMBO PI Dashboard and written so a second application can be brought to the same shape. Every code block below is real code from that app, not a sketch.

Written for two readers:

  • the same stack — React + TypeScript + Tailwind + zustand + react-router. Copy the modules; they have no dependency on this app's domain.
  • any other stack — each section ends with a Contract giving the data model and the rules with the React and the Tailwind taken out.

0The one idea

Anything the reader arranges is data, held per browser, and normalised against what the application actually offers today.

Every subsystem here is that sentence applied to a different surface:

surfacethe arrangementnormalised against
Left railsections, order, what is hiddenthe routes the app serves now
Nav iconsroute → icon namethe icon catalogue
Favouritesa list of routesthe routes that resolve
Feature flagsbooleansthe flag keys that exist
Themeone id + a token blockthe themes registered now
Published setupa file of the abovean allow-list, applied at both ends

The failure this prevents is specific and it is the reason for the whole pattern: a stored arrangement outlives the application it describes. A page gets renamed, a route retires, a filter value stops matching anything — and a naive JSON.parse(localStorage) hands the UI a shape that no longer means anything. In this app that produced a blank Architecture page with no control lit to explain it, because a stored filter selected a workstream that had been renamed. Everything below treats stored state as a preference, not a schema.

The precedence, everywhere, in this order:

1The left rail

1.1 The data model

The nav is not a list written in JSX. It is a document:

Items are routes, not page objects. That is the decision that makes the rest work: the layout can hold a page without knowing what the page is, a route the app stops serving simply drops out, and the same list can hold a board, an admin tool and a tree without a discriminated union.

The section with an empty label is the top of the rail — its items are drawn bare, with no heading.

1.2 normalise — the function everything else depends on

Four rules are load-bearing, and each one is a bug that was actually hit:

  1. Unknown routes are dropped. A retired page cannot leave a dead row.
  2. New routes are appended, never discarded. A page that ships and never appears in anyone's nav is a page nobody finds.
  3. hidden is claimed before sections. Otherwise a default layout — which lists every page by construction — makes hiding impossible.
  4. Empty sections survive. They are drop targets.

1.3 Moving things

The drag index rule is the one that costs an afternoon if you get it wrong. placeItem reads the item's current position before removing it, so a drop indicator sitting between two rows means the same thing whether the drag came from above or below. Without the from < index ? index - 1 : index correction, dragging downward within one section lands one slot too far, and only in that direction — which reads as a flaky UI rather than an off-by-one.

1.4 Migrations, so a rearrangement is never undone

Three helpers exist for the specific case of changing the app under an arrangement somebody already made. They are no-ops once the item has a place — including a place in the hidden tray — so they are safe to run on every render.

1.5 The catalogue — how the settings panel knows what exists

The shell is the only place that knows which pages survive the feature flags. The panel that arranges the nav is rendered from a different branch of the tree. A module-level store with subscribers is enough; a context provider for two values is more machinery than the problem.

Name the reader useNavCatalogue, not navCatalogue — a hook that does not start with use is a hook the linter cannot see, and rules-of-hooks will not protect it.

1.6 Icons as part of the arrangement

Once the reader arranges the nav, the icon becomes part of the arrangement — and the failure that follows is duplication, because a collapsed rail is icons and nothing else. Two entries wearing the same glyph are two rows you cannot tell apart.

So the picker's job is not "choose a pretty icon", it is show me what is taken and by whom. Store names, never components: a name is comparable, storable and testable.

The catalogue is hand-picked, not the whole icon set. A picker of fifteen hundred glyphs is a search box with no answer in it, and the point is telling entries apart — which needs icons that are unlike each other at 13px, not more of them.

1.7 Rendering the rail

1.9 Favourites

Favourites are the same idea one level up: the nav below is a complete map, which is right for finding something once and wrong for the three places somebody goes back to all day.

Two rules: it is absent entirely until something is starred — an empty "Favorites" heading is a promise the app is not keeping — and the star control lives at the bottom of the rail as "Add this page to Favorites", so starring is a thing you do to where you are rather than a thing you configure.

Contract — the rail without React

  • State: { sections: [{ id, label, items: string[] }], hidden: string[] }, plus navWidth: number, navCollapsed: boolean, navSectionsClosed: Record<label, boolean>, navIcons: Record<route, name>, favorites: route[]. All per browser.
  • Input from the app: a Map<route, { label, icon, why }> of the pages that exist after flags are applied, and the built-in layout.
  • The one required function: normalise(stored, known, fallback) with the four rules in §1.2. Without it the rest is unsafe.
  • Active-route rule: longest matching prefix wins.
  • Drag rule: read the item's current index before removing it.
  • Persist on every mutation; never on render.

2The top-right cluster, and the guide at the bottom left

2.1 The placement rule

This is the part most shells get arbitrary. One rule decides it:

A control belongs where the thing it produces will appear.
the control does thisit lives
navigates, and fills the content areain the left rail, as an ordinary row
changes how the page you are looking at behavesin the top-right cluster
needs the page still visible behind it while you decidea modal from the cluster
is a document about the appan overlay, opened from the rail

Applied here, it explains three moves that otherwise look like taste:

  • Admin tools are rail rows, not a gear menu. They open in the content area like any other page, so they belong with the other things that do that — and ordinary routes stay linkable, which a pop-up's contents are not.
  • Settings is a modal from the header, not a rail row. The flags decide what the rail lists, and a control inside that rail could switch itself off from under you. A modal also leaves the page you are checking the flag against on screen behind it.
  • The guide is an overlay, not a route. As a page it read as another section of the app — you could not tell whether you were looking at a window or a page.

2.2 The header

One sticky bar. Everything utility is pushed right with ml-auto, and every button shares one class function so the cluster reads as a set.

Two transferable habits:

  • buttonClassName as a prop. Each picker is its own component but wears the shell's class, so the cluster stays visually one thing and the components stay portable.
  • State badges live left, controls live right. The left of the bar says what you are looking at; the right changes it. Never mix the two.

Do not put filters here. Three rows of filter chips made this header 248px tall on every page, including the ones the filters did nothing for. Filters render inside the pages they act on.

2.3 The guide overlay, and the corner target

The generalisable pieces:

  1. Open and close on the same spot. The opener is at the rail's bottom left; the closer is a 112×112 corner of the sheet at the same place. Zero pointer travel for the round trip.
  2. The target is the corner, not the icon. A gradient marks it without drawing a box around it.
  3. Two closes, not one. The corner for someone who just opened it, the top right for someone who has scrolled a long document.
  4. Three ways out: the edge, Escape, and the button. Every overlay in the app behaves the same way, so none of them need to be learned.
  5. inset-3 on the sheet, not w-full inside padding — otherwise the gap lands on two edges out of four.

Contract — cluster and overlay

  • One class function shared by every header control; pass it into each as a prop.
  • Left of the bar = state; right = controls. Filters belong to pages.
  • An overlay dialog closes on: backdrop click, Escape, and at least one explicit control. If it covers its own opener, put a second close where the opener was.
  • A route that used to be a page keeps resolving, and redirects into the overlay with replace: true.

3Feature flags

3.1 What a flag is here

A flag is local to this browser. That is the whole distinction, and it is stated on the panel rather than implied by where the panel lives — everything else in Admin is shared with everyone reading the board.

They are plain booleans on the same settings store as everything else — not a separate system, not a provider, not a remote service. A flag that needs a network call to resolve is a flag that can fail.

3.2 The listing rule

A flag decides what is _listed_. The route always resolves.

Why: deep links from other pages keep working, and a page taken off the menu is still reachable by anyone who bookmarked it. In this app four sections are reachable and unlisted on purpose, each with the reason written at the constant:

The one case where a flag removes the entry and blanks the page is where the page itself is the thing being hidden — listing an entry that opens a notice saying it is hidden is the wrong half.

3.3 Flags that state their own reach

A switch that could do nothing looks like a switch that is broken. Where a flag reveals data, count what it would actually reveal in the dataset loaded right now, and put that number on the switch:

These used to quote fixed numbers in their descriptions. A dataset ingested before the test matrix existed carries no status at all, so the switch had nothing to reveal and no total moved when it was flipped — while the description still said 859. Counting the loaded records means an inert switch says so.

3.4 What each flag entry carries

restart matters more than it looks. A switch whose effect appears two navigations later is indistinguishable from a switch that does nothing.

3.5 Session locks are not preferences

One flag in that list is deliberately not persisted across a reload:

It is forced back to its safe value on load, and it is excluded from the publishable set. Anything that protects data belongs in this category.

Contract — flags

  • Booleans on the same per-browser store as every other preference.
  • flag?: keyof Flags on the nav entry; routes never gate on flags.
  • Each flag ships with: label, one-line detail, optional "applies when", optional live count of what it would reveal.
  • Session locks re-arm on load and never publish.

4Theming

4.1 The idea that makes it cheap

Write the remap once, against custom properties. A theme is then data.

The app uses a small, consistent Tailwind surface vocabulary — bg-white, bg-slate-50/100/200, one accent ramp. A theme is expressed by remapping that vocabulary, not by writing parallel markup. Every board, drawer, grid, popover and settings module follows automatically, and a new theme is a token block rather than another 120 rules.

Two things about that:

  • The rgb(var(--token) / .95) form is why the surface tokens are stored as bare channel triples (248 250 252) rather than hex — it is the only way one token serves both the solid and the translucent class.
  • Enumerate the opacity variants you actually use. There is no wildcard. Grep the markup once and write those lines; a missed one shows as an unthemed patch on exactly one panel.

4.4 The dark class caveat

If the markup contains Tailwind dark: variants, exactly one theme may carry the literal dark class. Other themes fall through to the light branch — which is what a light palette theme wants anyway.

A specificity trap comes with it. Tailwind emits dark: utilities as .dark\:x:is(.themed *), which outranks a plain .dark rule, so overrides have to be written against html.dark:

Cleanest advice for a new app: do not use dark: variants at all. Express dark as another token block. The variants exist here only because they predate the token system.

4.5 Themes derived from a palette

Themes beyond the built-ins are generated: give a list of hex values, get a token ladder. That engine has no dependency on the app and lives in its own folder, already packaged to be lifted:

Its README states the boundary, and this is the boundary to copy:

It depends on React and nothing else — no CSS framework, no icon library, no state manager, and no import from the application it happens to be sitting in. Styles are injected at runtime from a string, scoped under .ts-studio, so there is no stylesheet to wire into a bundler and no class names that can collide with the host's. The component is fully controlled: it owns no palettes and persists nothing. Where palettes are stored — localStorage, a file, an API — is the host's decision, which is what makes the component portable.

Custom themes are held in a module variable rather than a store, because applyTheme runs outside React:

themeMeta falls back to the first theme rather than throwing. A stored theme id that no longer exists is the same class of problem as a stored route that no longer resolves, and the answer is the same: degrade, do not fail.

Contract — theming

  • One CSS file maps your framework's surface vocabulary to custom properties, gated on a single .themed class. Enumerate the opacity variants you use.
  • Surface tokens are channel triples so rgb(var(--t) / .5) works.
  • A theme = { id, label, className, colorScheme, tokens }. Applying it = clear all custom properties, set the class, write the tokens, set color-scheme.
  • Unknown theme id → first theme, never an exception.
  • Keep the derivation engine dependency-free and fully controlled.

5Publishing a setup, so an arrangement travels

Everything above is per browser, which is right for a preference and wrong for a setup. An arrangement somebody spent a week getting right does not survive opening the app on a second machine, and no amount of pulling the repo fixes it — git carries the code, never the browser.

5.1 Two mechanisms, because there are two shapes of state

The settings store is a bag of independent keys, so it merges one setting at a time. A grid view or a palette set is a whole document with no per-key merge logic, so it travels whole, keyed by its storage name.

5.2 The allow-list for settings

An allow-list, not a deny-list — so a setting added later is excluded until somebody decides it should travel.

Two categories are excluded on purpose, and the reasons generalise:

  • Session locks. A value that re-arms on every load would be published as a default that is overwritten a line later.
  • Migration markers. A repair-version number records what has been done to one stored layout. Shipping it would tell a fresh browser that repairs had already run against an arrangement it has never seen.

A third is worth calling out because it is a judgement, not a mechanism: the coverage-package selection is deliberately not shareable. Which data a reader is measuring against is a question they are asking right now, and a published preset that pinned it would decide for everyone whose browser loaded the file, silently, on the one number people quote.

5.3 The allow-list for whole stores

Three categories must never travel, and each would do real damage:

  • Work in flight — unsaved edits. Replaying one machine's half-finished edits onto another is data loss wearing a feature's clothes.
  • Content — a journal is a record of what happened, not a preference. A "reset to defaults" that can erase a journal is a bug.
  • This machine's diagnostics — a recovery log would make a fresh machine believe it had been crashing all week.

LOCAL_ONLY carries a why per key so the settings panel can say what stays.

The allow-list is applied at both ends, because the file is data and may be hand-edited. Filter on collect and on seed.

That two-source fallback is what lets the same preset work in a dev server, a static build and a single-file offline build. Nothing published is the ordinary state, not an error.

5.5 Boot order — the part that is easy to get wrong

A store that reads localStorage at import time builds its initial state the moment it is imported. So anything meant to change what "no preference" looks like has to be installed before that import — which means a dynamic import of the app.

5.6 Where precedence is actually enforced

The trap in that block, spelled out. Every validated key must fall back to base, not to a literal [], {} or null. Falling back to a literal silently discards the published value on precisely the browsers the preset exists for — the fresh ones. It is invisible in testing, because the developer's own browser has something stored.

5.7 Publishing

One definition, two callers: the App defaults panel where publishing is the deliberate act, and the standalone build, which publishes first so the file it cuts opens into the current arrangement. That second caller is the reason the function exists — asking people to remember the order made the correctness of the artifact depend on a habit.

5.8 Saving must never take the app down

The quota is about 5 MB and this blob carries the nav layout, its icons, favourites, the roll-up layout and the field order. A private window can refuse writes outright. A throw inside a store setter travels up through the React event handler — which, before an error boundary existed, meant a white screen from adjusting a setting.

Contract — publishing

  • Two allow-lists: per-setting keys, and whole storage keys. Both filtered on write and on read.
  • Never publish: work in flight, content, machine diagnostics, session locks, migration markers.
  • Seeding fills in only where the browser has nothing. A deliberate reset may overwrite.
  • Install published defaults before importing anything that reads storage.
  • Every validated key falls back to the published base, never to a literal.
  • Storage writes are wrapped and warned once.

6Porting checklist

Roughly a day for the first four, in this order. Each step leaves the app working.

  1. Token pass. Pick your surface vocabulary, define :root, write the .themed remap, add a light and a dark theme. Nothing else changes yet.
  2. Settings store. One store, one storage key, persistSettings with the try/catch, built-in defaults as a plain constant.
  3. Rail as data. Add NavLayout + normalise, write your BUILT_IN_NAV, render sections from it. The rail should look identical when you finish.
  4. Arrange it. Width drag, collapse, fold state, then the settings panel with placeItem / moveItem / hideItem.
  5. Flags. Booleans on the store, useListed, flag? on nav entries only.
  6. Header cluster. One shared class function, state left, controls right.
  7. Guide overlay. Backdrop + Escape + two closes, one under the opener.
  8. Icons and favourites, if the rail is long enough to need them.
  9. Publishing, last — it is the only step that needs a server endpoint.

What to keep tests on

The pure modules carry the whole risk, and they are pure precisely so they can be tested without a DOM:

  • normalise — dropped, appended, hidden-wins, empty-section-kept.
  • placeItem — same-section drag in both directions.
  • moveItem — crossing a section boundary, stepping into an empty section.
  • shareable / isPortable — an excluded key cannot get through either end.
  • resolveIcons — unknown name falls back rather than leaving a hole.
  • tabOwnsPath — nested routes.

7The traps, collected

Each of these cost real time here.

  1. An ElementTree/DOM-ish object that is falsy. Not JS-specific, but the general form is: a || b where a is a valid-but-falsy value silently takes b. Use != null checks for anything that can legitimately be empty.
  2. A stored value that no longer matches anything narrows a view to zero with no control lit to explain it. This is why normalise exists, and why the filter state needed the same treatment as the nav.
  3. [hidden] loses to an inline display. A UA rule cannot beat a style attribute. If you toggle hidden, do not also set display inline.
  4. A drag index read after the item is removed shifts every list by one, and only in one direction.
  5. Two nav entries both marked active, because a prefix match claims a nested route. Longest match wins.
  6. window.innerWidth is 0 before the first layout. A default computed at module scope silently takes the fallback. Read it lazily, and ask document.documentElement.clientWidth as a second question.
  7. A validated setting falling back to a literal instead of the published base — invisible on any machine that already has settings stored.
  8. A theme switch leaving the previous theme's tokens behind. Clear all custom properties before writing the new ones.
  9. A localStorage write throwing on quota or in a private window, taking a render down with it.
  10. A flag whose effect is deferred, with nothing on screen saying so — it reads as broken. Say when it applies.
  11. A switch that reveals nothing in this dataset while its description quotes a fixed number. Count what is loaded.
  12. Tailwind opacity variants are separate classes. bg-slate-50/95 needs its own remap line; it does not inherit from bg-slate-50.
